# 性能优化：电脑卡顿（大库 ~141 万产品）

日期：2026-11-09（Asia/Shanghai）  
范围：启动/首页/列表滚动/搜索/侧栏计数/状态栏轮询；**未打包、未传电脑**。

## 卡顿根因（定位）

在 `data/crawl/producthub.db`（约 141 万行）上测到的主要热点：

| 热点 | 优化前 | 说明 |
|------|--------|------|
| `/api/facets` 来源计数 | **~6439 ms** | `COUNT(DISTINCT product_guid)` 扫 `product_versions` |
| `/api/analytics` 全表扫 tags | **~6591 ms** | 侧栏每次切页都打，解析 140 万行 tags JSON |
| `/api/enrich/status` | **~6030–7750 ms** | 状态栏 1.5–6s 轮询全表 `SUM/COUNT(*)` |
| 首页 `ORDER BY launch_date, launch_count, votes` | **~6760–6850 ms** | 用不了 `idx_products_launch`，TEMP B-TREE 全表排序 |
| 搜索结果非相关度排序 | 可达 **~1400 ms+** | `SELECT guid FROM products ORDER BY …` **全表**再 filter 命中集 |
| 列表 `SELECT *` | 传输/解析偏大 | 含 `description` / `enrich_json` / `embedding` / `ai_analysis` |
| 侧栏依赖 `[view]` | 每次导航重打 analytics/home | 与抓取并发时 `db.rev` 狂涨，无 TTL 时缓存几乎无效 |
| 调度器 | 启动即 tick + status 每次 `dueSources(1000)` | 与 UI 冷启动抢 CPU/磁盘 |

## 已落地改动

### 后端
- **列表瘦身**：`LIST_COLS` + `hydrateList`（`products.ts` / `filter.ts` / `home.ts`），默认不返回大字段。
- **禁止全表排序命中集**：`orderHitGuids` 只对搜索命中 guid 排序（`filter.ts`）。
- **facets**：改读 `sources.product_count`（维护于抓取），并 `memoByRev`。
- **侧栏轻量接口**：`GET /api/nav-stats` → `navAnalytics`（分类计数 + 热度标签抽样）；完整 `/api/analytics` 仍给分析页，且按 rev/TTL 缓存。
- **home**：走索引的 `ORDER BY launch_date DESC, first_seen DESC`；近窗分类/趋势改为「索引取最近 4000 条再分组」；整体 `memoByRev`。
- **status / enrichCounts**：聚合结果 `memoByRev`（默认 **30s TTL**，抓取时不因 rev 抖动打穿）。
- **searchAll**：物化上限改为约 8000（FTS 候选本就 ≤3000）。
- **scheduler**：启动后 **45s** 再首轮 tick；`due` 计数 30s 缓存。
- **SQLite**：`busy_timeout=5000`，降低与并行抓取的 `SQLITE_BUSY` 硬失败。

### 前端 / Electron
- 侧栏改打 `/api/nav-stats`，依赖 `status.products/last_sync`，**切页面不再重打重查询**。
- 产品列表分页 `PAGE`：**100 → 40**（虚拟表仍在）。
- Electron：`backgroundThrottling: true`，`spellcheck: false`。

## 仍存瓶颈

1. **`alternative to X` / findSimilar**：单次可达 2–3s（alt_rel + 多目标相似），体验上仍是「搜一下顿一下」。
2. **按分类浏览**：`category + ORDER BY updated_at` 缺少复合索引，常见 0.4–1.7s；加 `(category, updated_at DESC)` 需在空闲时 `CREATE INDEX`（大库会锁写一段时间）。
3. **`/api/analytics` 首次**（分析页）：全表 tags + 重 JOIN 仍可能 **数秒～十余秒**，已缓存，但首次打开分析页会卡一下。
4. **enrich 全表 SUM 首次**：状态栏首次仍可能卡；之后 30s TTL。可考虑落 `settings` 计数器由抓取增量维护。
5. **结构化筛选 + 关键词**：仍可能 `SELECT guid WHERE …` 拉出巨大候选 Set。
6. **并行抓取写库**时：UI 查询会 `busy` 等待，体感卡顿与优化正交——增量抓取尽量错峰或降并发。
